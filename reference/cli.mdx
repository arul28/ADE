`daex` is the typed control plane for Daex. Everything you do in the desktop app — create lanes, run agents, ship PRs, kick off tests, attach Linear issues — has a CLI command, so you can drive Daex from any shell. Agents running inside Daex use the same commands, which is how they inspect and operate the workspace they live in.

<Note>
The command used to be `ade`, and `ade` still works as an alias for `daex`, so existing scripts and habits keep running.
</Note>

```bash
daex lanes create "fix-checkout-flow"   # spin up a worktree for a task
daex brain status --text                # check the machine runtime
```

<Tip>
Two commands discover everything: `daex <group> --help` for exact flags on any command, and `daex actions list --text` for the full service-backed action catalog behind the typed commands.
</Tip>

## Output modes

Most commands take an explicit output mode. Use `--text` for a human-readable summary and `--json` for stable, scriptable fields (the default when output is piped).

```bash
daex lanes list --text   # readable summary
daex lanes list --json   # stable JSON for scripts and agents
```

## Command groups

<AccordionGroup>
  <Accordion title="Project & lanes" icon="code-branch">
    Register projects and manage worktrees (lanes).

    ```bash
    daex init                                # add the current directory as a project
    daex projects list --text                # list registered projects
    daex lanes list --text                   # list lanes in the active project
    daex lanes create "fix-checkout-flow"    # create a lane from the default branch
    daex lanes create --name auth-ui --from auth-base --on local
    daex lanes delete <lane-id> --force --delete-branch
    ```
  </Accordion>

  <Accordion title="Chats & sessions" icon="comments">
    Start and inspect agent chats, terminals, and CLI sessions inside a lane.

    ```bash
    daex chat list --lane <lane-id> --text
    daex chat create --lane <lane-id> --model gpt-5.5
    daex shell start-cli codex --lane <lane-id> --permission-mode edit --message "fix failing tests"
    daex shell start --lane <lane-id> -- npm test
    ```
  </Accordion>

  <Accordion title="Git & PRs" icon="code-pull-request">
    Commit, push, and turn a lane into a pull request; read CI and comments.

    ```bash
    daex git commit --lane <lane-id>
    daex git push --lane <lane-id>
    daex prs create --lane <lane-id> --base main --title "Fix checkout flow" --text
    daex prs list-open --text
    daex prs checks <pr> --text              # CI status for a PR
    daex prs comments <pr> --text
    ```
  </Accordion>

  <Accordion title="Tests" icon="flask">
    Run test suites in a lane.

    ```bash
    daex tests run --lane <lane-id> --suite unit --wait
    ```
  </Accordion>

  <Accordion title="Linear" icon="list-check">
    Attach and update Linear issues through Daex's own Linear connection — no API key needed.

    ```bash
    daex lanes create --name ENG-431 --issue-id ENG-431 --start-chat --provider codex --type subagent
    daex linear attach --this-session --issue-id ENG-431
    daex linear comment "Pushed a fix; CI running"
    daex linear set-state ENG-431 <state-id>
    ```
  </Accordion>

  <Accordion title="Account & machines" icon="user">
    Link this machine to your Daex account so you can reach it from Daex desktop,
    the web client, and iOS. `daex connect` is idempotent — re-running it on a
    connected machine just prints status.

    ```bash
    daex connect                             # sign in, install the service, publish this machine
    daex connect --status --text             # report the three steps, change nothing
    daex connect --headless                  # sign in from another device: QR code, link, and code
    daex connect --no-login                  # service only; stay local/LAN-only
    daex connect --no-service                # account only; skip the login service
    daex connect --timeout 120               # seconds to wait for the machine row (default 60)
    daex login                               # sign in without touching the service
    daex machines list --text                # machines registered to this account
    daex machines reconnect                  # re-pair this machine after it was removed
    daex logout                              # undo the account half of connect
    ```

    The machine row is published by the running brain, not by this command — so
    the brain must stay running for the machine to remain reachable. Full
    walkthrough, including running the brain on a Linux server:
    [Connect a machine](/getting-started/connect-machine).

    Removing a machine from your account is deliberate and terminal: heartbeats
    never re-register it, and its Activity, notifications, and Live Activities
    stop. `daex machines reconnect` is the way back. It takes no selector — it
    always re-pairs the machine you run it on — and it needs proof of a freshly
    completed interactive sign-in, so it prompts for one when the account
    directory asks and finishes the re-pair as soon as that lands. Only once the
    directory accepts does it lift the push gate, so Activity, alerts, and
    badges resume without restarting the brain. A normal `daex login` runs the
    same repair automatically, and Daex desktop offers it as **Reconnect this
    computer** in Settings.
  </Accordion>

  <Accordion title="Brain & pairing" icon="microchip">
    Control the machine-owned Daex runtime (the brain) and pair a phone.

    ```bash
    daex brain status --text                 # endpoint, service, and sync state
    daex brain start                         # load the login service
    daex brain stop                          # unload the login service
    daex brain restart                       # re-exec after an app update
    daex brain pin generate                  # generate a phone pairing PIN
    daex brain pin set 123456                # set an explicit pairing PIN
    ```
  </Accordion>

  <Accordion title="Proof" icon="camera">
    List the computer-use proof artifacts Daex captured for a chat or session.

    ```bash
    daex proof list --arg ownerKind=chat --arg ownerId=<session-id>
    ```
  </Accordion>

  <Accordion title="Discovery" icon="compass">
    Find commands, flags, and the full action catalog, and check local readiness.

    ```bash
    daex <group> --help                      # exact flags for any command
    daex actions list --text                 # full service-backed action catalog
    daex actions run git.stageFile --arg laneId=<lane-id> --arg path=src/index.ts
    daex doctor                              # local runtime, git, provider readiness
    daex triage                              # hand a broken install to a coding agent Daex has downloaded
    daex triage --agent --text               # print the context + playbook paths instead of launching one
    daex skill list --text                   # bundled agent skills
    ```
  </Accordion>
</AccordionGroup>

<Note>
Prefer typed commands — they validate arguments and return stable fields. Reach for `daex actions run <domain.action>` only when no typed command covers the workflow yet.
</Note>
