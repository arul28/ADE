# iOS Companion

The DAEX iOS app (`apps/ios/`) is a native SwiftUI client. The phone never runs
agents. It works two ways, with the same tabs:

- **With a computer**: a controller for a `daex serve` brain on one of the
  person's computers. It reads synced state from a local SQLite replica and
  sends commands over the sync WebSocket.
- **With no computer**: DAEX Cloud. Saved chats, copies, Git summaries, files
  and history come from the account server and GitHub; a cloud computer wakes
  only to do work (see [DAEX Cloud on the phone](#daex-cloud-on-the-phone)).

Wire, pairing and security rules shared with the desktop are in the
[sync README](README.md). Code identifiers keep `ADE` (`ADEApp`,
`com.ade.ios`, `ade.*` defaults keys, `ADE1` frames).

## Connect your phone

The phone connects to a **machine**, named by its account custom name, else its
computer name; routes are never part of the name.

1. **Account sign-in** (main path): the phone adopts a same-account machine with
   no PIN, over LAN, Tailscale, then Relay. LAN and Tailscale need the host's
   Ed25519 key in the directory and a verified sealed `ade-adopt-v1` challenge;
   an unsigned host is Relay-only. The account token is memory-only.
2. **Direct recovery**: the This computer card on the computer owns the PIN and
   QR. Scan the QR or pick it from Nearby, enter the 6-digit PIN. The phone
   keeps a per-device secret in Keychain.
3. Pick a project.

A signed-out launch shows the account choice first; a phone with a paired host
may **Continue to your work** on cached data.

- **Secret kept after adoption.** `syncResolveAccountHelloPairedSecret` mirrors
  `resolveAccountHelloPairing` (`apps/desktop/src/shared/accountDirectory.ts`):
  no `accountPairing` in `hello_ok` means keep the secret already held.
- **Sign-out** closes Relay and keeps direct trust for LAN/Tailscale. **Forget
  machine** is the only trust delete. "Sign out of this iPhone" or a different
  account also runs `SyncService.resetLocalReplicaAfterAccountLeft` (replica
  file and site id removed, so no change rows sync back).
- **Vault boundary.** The phone never receives vault values; it uses only the
  settings commands the host advertises.

### Pair with SSH

A one-time bootstrap for a Mac with DAEX: key sign-in, `SHA256:` host key
trust-on-first-use, then `daex sync pair-device --json-stdin` with the phone's
DPoP identity. Ed25519 (encrypted or not) and unencrypted ECDSA keys; RSA is
refused. A key is kept only for the session unless SSH recovery is on (then in
Keychain behind biometrics, never synced).

## DAEX and DAEX Beta

- **DAEX** (`com.ade.ios`) gets stable releases.
- **DAEX Beta** (`com.ade.ios.beta`, `ADE_BETA_APP`) gets every beta from
  `ios-testflight.yml`: its own App Group, orange icon, `daex-beta://` scheme,
  no App Clip.

They share no data or pairings and one build-number sequence, so
`MIN_SUPPORTED_MOBILE_APP_BUILD` means the same for both.

## Host version compatibility

- **Protocol range** `1...1`; outside it the host sends
  `protocol_version_mismatch` and closes `4406`; the phone says which side to
  update.
- **Feature level.** `features.mobileCompatibility` is `full` or `limited`; an
  omitted one is limited. Missing actions fail before they are queued, with an
  "update DAEX on the machine" message.
- **Update another machine** (`MachineUpdateStore.swift`): `machine.updateImpact`
  first (what the restart stops), then `machine.updateAndRestart`. The newest
  build per track comes from `GET /releases/latest`. `updateInstallMode:
  "manual_download"` shows **Download the update**. DAEX Cloud computers update
  themselves.
- **App Store check** (`AppUpdateAdvisor`): at most once in 6 h.

## Slim mobile chat wire

The phone sends `mobileChatSlimV1`; the host applies
`apps/desktop/src/shared/chatMobileSlim.ts` to the live stream only:

- Drop the dot-family `subagent.progress` twin when its underscore original was
  just sent.
- Progress is state: the snapshot keeps the latest per agent; live, at most one
  per agent per second.
- Tool results arrive capped at 2 KB with the true size and
  `resultTruncatedForMobile`; expanding sends `chat_tool_result` (needs an
  active subscription).

## Chat details

### Chat Info

- **Scheduled work.** Cancel shows only for an active durable row when
  `canInvokeChatRemoteAction` confirms `chat.cancelScheduledWork` (not
  queueable). Pause/Resume use `chat.setScheduledWorkPaused`. Personal chats map
  to `personalChats.*`.
- **Account row** (`WorkChatAccountNote`): provider and account from the chat's
  `instanceId`, read from `providerAccounts.list` on the chat's machine; may
  open "Run this chat on" (`chat.switchAccount`).
- **Sections** mirror the desktop drawer (Subagents, Background, Schedule; caps
  12 / 8 / 10; a Completed fold).
- **Subagents.** An in-thread subagent (native Task) has a card, not a
  transcript. A spawned child chat is a full chat; its row opens it on its own
  machine.

### Model picker

- The pill reads its label from the live `chat.modelCatalog`.
- **Custom** lists the machine's saved harness presets when the host advertises
  `account.getMachineInventory`; a pick passes `presetId`. Presets never send
  keys.
- **Free** reads `freeModels` from `ai.getStatus` on the chat's machine
  (`WorkFreeModels.swift`); **Get free models** runs `ai.pinnedToolDownload`. A
  machine with nothing signed in starts new chats on the free default.
- `WorkModelPickerSheet` merges providers per group (`workMergedProvidersByKey`,
  because SwiftUI traps on duplicate `ForEach` ids) and is a `LazyVStack`
  (one provider can list hundreds of models). `ModelPickerListRow` is
  deliberately not `Equatable` (it would keep stale closures).

### The transcript surface

- **The user's bubble paints on the tap frame**: the local echo is appended to
  the snapshot synchronously; image sends echo before upload under an
  `ade-pending-upload://` placeholder. Echo suppression counts rows
  (`workUnrepresentedLocalEchoMessages`), so two identical sends both show.
- **The transcript is a `UICollectionView`** (`WorkChatTranscriptCollectionView`)
  with SwiftUI rows in hosting cells, because UIKit compensates its offset when
  a cell self-sizes. Heights are cached by row id, width and revision; a row
  whose content changed is reconfigured, never re-inserted
  (`workChatTranscriptRowRevision`).
- **One latch decides scroll writes** (`workChatFollowLatch`, unit-tested). Only
  `performScrollWrite` moves the viewport and it ignores writes under 0.5 pt.
  While not following, the reader's top row is the anchor and is restored after
  each layout pass. A chat opens at the tail in one frame. Revealing buffered
  history requires not-following.
- `ADEUITests/WorkChatScrollBenchUITests.swift` is the acceptance test.
- **Messages render whole**; "Open full response" (`WorkOutputViewerScreen`) is a
  searchable reader. Boxed renderers clip and open the viewer. **Copy is always
  the full content.**
- **Long replies cost O(tail)**: streaming markdown and highlighting reuse a
  stable prefix; block ids are positional; caches drop on memory warnings.
- Startup diagnostic cards fold into one row (`foldingWorkDiagnosticCards`).

### Select, copy and comment on a reply

Long replies are one cell per markdown block. The long-press menu
(`WorkMessageTextSelection.swift`) offers Copy message, Copy this part, Select
text, and Comment on this part (when the host takes `chat.createThreadComment`).
Select text opens a read-only `UITextView` sheet. A comment carries a text anchor
(`WorkMessageSelectableDocument.swift`, the twin of desktop `captureTextAnchor`),
the shared message key and one `clientId` per draft, so a retry returns the same
comment.

## Connection UI

- Every indicator reads `SyncConnectionHealth` (`SyncService.connectionHealth`):
  `transport` (`disconnected`, `connecting`, `connected`, `unreachable`) and
  `load` (`strained` after recent timeouts). There is no "syncing" state;
  hydration is `SyncDomainStatus`. "Attached?" is `SyncService.isAttached`.
- The toolbar control (`ADERootToolbarControls`) shows dot, state and machine
  on every screen; screens show no offline cards of their own. The Hub shows
  `HubNoMachineState` with Reconnect.
- The route badge (`via LAN` / `via Tailscale` / `via DAEX Relay`) shows only
  after an authenticated connect.
- **Project host not ready.** On `host_unavailable`, a verified conflict opens
  `ProjectHostRecoveryScreen` (mirror of `shared/syncHostRecoveryUi.ts`); a
  starting failure retries 2/4/8 s behind one banner. **Fix connection** calls
  `sync.recoverHost`.
- **Domain failures** show one card per tab (`SyncDomainFailureNotice`) with
  Retry. Failed turns show an instruction card, never "Error".
- `ADETailscaleOffHintCard` shows only when turning Tailscale on is the one fix
  (`syncShouldShowTailscaleOffHint`: tailnet route saved, no `utun*` tailnet
  address, no relay candidate, not connected).

### Machine naming and reachability

- `AccountMachine.displayName`: custom name, hostname, platform fallback;
  `rowLabel` adds the install ("MacBook Pro · DAEX Alpha").
- State order: **Asleep** (recently announced), **Connected**, **Online**, then
  **Last seen**. `accountMachinePowerClause` must match desktop
  `machinePowerPhrase` word for word, and `SyncMachineWake.swift` must match
  `resolveMachinePresence`.

### Waking a sleeping Mac

Dialing is the wake: `pairWithAccountMachine` runs with
`SyncConnectionRaceBudget.wakingMachine` (25 s overall, 22 s for relay ready)
and the words change ("Waking <machine>…"). `MachineWakeCard`
(`SyncService+MachineWake.swift`) runs confirm → waking → failed. Links carry
`accountMachineKey`; `DeepLinkRouter.routeOwned` waits for the account, connects
the machine (Wake & open), waits for the live catalog, then opens the item. Only
external links infer an owner, never a cold-launch restore.

## DAEX Cloud on the phone

Every cloud computer is shown as "DAEX Cloud" (`CloudLaneComputerLabels.label`).

- **Reading never wakes**: saved chats, copies, Git summaries, files, history,
  the CTO copy, Linear and Settings › DAEX Cloud come from the account server or
  GitHub. `MachineFleet.connect(…, wake: false)` connects only to a computer
  already up.
- **Doing wakes**: a send, "Wake and open", "Wake to use it", "Wake and move".
  `beginCloudWakeIfAsleep` is the one waker (a second wake joins the first).
- **Account scope.** A Hub card no reachable computer holds opens the tabs in
  account scope (`openAccountProjectScope`, id `account:<id>`); host commands
  throw "Pick a lane on a computer or on DAEX Cloud."
  (`refuseAccountProjectScopeCommand`) and never queue.
- **New chat.** The machine picker always lists DAEX Cloud; the model sheet is
  fed by `GET /cloud/models`. Files upload first
  (`PUT /cloud/launches/:launch/files/:file`), then `POST /cloud/launches`. The
  launch page (`WorkCloudLaunchPendingScreen`) takes follow-ups
  (`POST /cloud/launches/:launch/messages`) and swaps to the chat once it runs.
- **Saved chats** read from the account (`CloudServerClient.savedChats`, pages of
  200) and page older parts with `before`. A saved proof shows the picture the
  computer saved (`savedChatProof`).
- **The queue.** A send with no live link goes to
  `POST /cloud/chats/:machine/:chat/messages` with `clientSendId` as the message
  id. A live send to a cloud chat waits 10 s for an answer, then the same id goes
  to the queue (the computer dedupes by id). Held messages draw as the person's
  own bubbles (`CloudHeldMessageRow`) and retire when the transcript shows the
  matching `clientSendId`.
- **CLI and shell copies** (`GET /cloud/projects/overview`, at most once in 15 s)
  list as `cloud-copy:<machine>|<session>` rows, read-only; a deleted CLI takes a
  message (continues on a new computer); a deleted shell cannot.
- **Lanes at rest** (`CloudLaneAtRestScreen`): Git summary
  (`GET /cloud/git/:machine/:lane`), files and history from GitHub. **Move to…**
  sends `chat.startCrossMachineBatchMove` to the lane's computer; DAEX Cloud is
  never a destination.
- **CTO, Linear, Settings.** The CTO account copy (`GET /cloud/cto`); Linear via
  `POST /cloud/integrations/linear/query` (2 pages per load; writes need a
  computer); Settings › DAEX Cloud reads `/cloud/account`, `/cloud/instances`,
  `/cloud/limits` and `/cloud/sign-ins` (status only); Settings › Machines shows
  one DAEX Cloud row.
- An old server (404) keeps today's behavior; a failed read keeps the last answer.

## Database: native SQLite + pure-SQL CRR

`Database.swift` uses system SQLite with cr-sqlite emulated in SQL triggers (see
[crdt-model.md](crdt-model.md)). First launch creates
`Application Support/ADE/ade.db`, loads `DatabaseBootstrap.sql`, registers
`ade_next_db_version`, `ade_local_site_id` and `ade_capture_local_changes`,
enables CRR triggers per table, and saves a stable site id.

**Every column the desktop can write must exist here.** An unknown column fails
the batch and stops sync until an app update, so each replicated column is
mirrored with `ensureColumn` (nullable, no unique index). An unknown table's
rows are skipped. `adeDatabaseDidChange` carries the touched tables so only the
affected projection revision bumps.

## Sync service

### Connection lifecycle

1. **Connect.** `reconnectIfPossible` owns every attempt (coalesced,
   generation-guarded, never tears down a live connection). Direct candidates get
   parallel TCP probes; Relay candidates (from the QR and `cloudRelayWssUrl`) are
   whole routes, eligible only when `relayAccountOwnerId` matches the signed-in
   account, each with a fresh token.
2. **One race** (`SyncConnectionRace.swift`): `lan` < `tailnet` < `relay`, Relay
   ~300 ms behind the lead (t=0 when it is this network's proven route), 250 ms
   stagger, three sockets, 10 s budget; only `hello_ok` wins. Relay URLs use
   `ready=2` (350 ms for `accepted`, 7 s for `ready`). A single-flight registry
   refuses a second `/connect` for one machine.
3. **Wire options**: `chunkedEnvelopes`, `binaryEnvelopes` (because
   `URLSessionWebSocketTask` has no permessage-deflate), `foldedReplay`,
   `deflate`, 32 MiB frames.
4. **Pairing rejection.** The phone drops a pairing only when the rejecting host
   names itself and matches, or when a finished race got only rejections from
   one host. Account and host-update codes never drop it.
5. **Hydrate.** Lanes and Work in parallel gate the first screen; PRs alongside.
   Every request is scoped to its connection and project and re-checks before it
   writes. PR hydration uses `prs.list`, then bounded `prs.refresh` batches of 25
   for open PRs and live lanes.
6. **Steady state.** Inbound decoding and apply run off the main actor, in order.
   Phone changesets are one durable pending batch; the cursor moves only on ack;
   retries shrink windows (64 rows / 64 KB down to 1 row / 4 KB).
7. **Disconnect.** Seven fast attempts (1 → 16 s), then `unreachable` with a
   quiet 30–40 s retry. `SyncReconnectFlapTracker` backs off when a host keeps
   closing right after hello. A project route used in the last 24 h restores on
   launch.
8. **Lane presence**: announce on open, release on leave, 30 s heartbeat.

### Foreground resume

iOS suspends background sockets without a close. `syncForegroundResumeAction`:
a gap of 10 s or more rebuilds the session; under 10 s refreshes and probes
liveness in parallel; a cold start only refreshes. Every foreground resets the
reconnect ladder.

### Switching machines

`SyncConnectAttemptTarget` names the machine a connect aims at. A failed switch
reconnects the previous profile (`restorePreviousConnection`). Do not read
success from `connectionState`: `reconnect(toSavedHost:)` returns whether that
host was reached.

### Route ranking, route memory, and roaming

- `syncRankedEndpointAttempts`: not demoted, live discovery, class, latest
  success; `networkRouteMemory` (8 entries keyed by `wired`, `wifi:<IPv4 /24>`
  or `cell`) hoists the route that last worked on this network.
- Demote (never remove) after two failures in 120 s, and private addresses with
  no Wi-Fi.
- **Roam** (make-before-break) only on an interface change (failover, 3 s floor)
  or an upgrade probe toward a better class (once in 5 minutes).

### Message rules

- **Terminals.** `terminal_data.offset` is a lifetime UTF-8 offset. Gaps trigger
  one guarded `sinceOffset` resubscribe; `terminal_history` pages older bytes.
  Input with `terminalInputAck` has a stable `inputId`, one in flight per
  session, 8 s wait and retries; the host dedupes. Phone resizes are not
  authoritative. `features.rosterTerminal` serves terminals on a roster
  connection for any open project on that machine.
- **Chats.** `chat_subscribe` with `sinceSeq`; first tail 256 KiB; `chat_history`
  pages 256 KiB. Project chat subscriptions stay warm 120 s (max four). Frames
  decode off the main actor into `ChatThreadRegistry`, at most one frame per
  display frame. `chatLogV2` hosts get `sinceSequence` + `generation` resume; a
  different generation drops the chat's cache. When the brain moved to another
  project, the host still serves the chat from disk, or answers `unavailable`
  for phones with `chatSubscribeUnavailableV1`; after 15 s the phone switches it
  back (at most once per 10 minutes per machine). Personal chats subscribe with
  `chatScope: "personal"` and call `personalChats.*`.
- **Roster.** `roster_snapshot` then `roster_delta`; `toolType` routes chats to
  the chat view and CLI rows to the terminal.

### Offline behavior

Synced state reads offline. Commands queue with their project scope and replay
with the same `commandId` (the runtime dedupes). **A live `chat.send` with an
unknown outcome is never replayed**: the draft is restored. `host_unavailable`
is retryable. Offline `chat.create` shows a `pending-create:<commandId>` row.

### Timeouts

Default 30 s; `chat.send` 120 s ("DAEX couldn't confirm whether this message
started…"). A timeout does not drop the connection when any envelope arrived in
the last 12 s; otherwise the phone probes liveness (ping, then 5–12 s by path).
`InitialHydrationGate` waits up to 15 s; do not raise it.

## iOS services

- **Keychain** (`KeychainService.swift`): paired secrets and per-machine tokens
  (`connection-token.<machineKey>`). **A failed read changes nothing**: only
  `errSecItemNotFound` means absent; any other error (before first unlock) must
  not re-key, rewrite or mint. The device id is provisional until Keychain reads.
- **PIN pairing.** QR payload v3 (`PairingQrPayload.parse`, never a code);
  `pinConfigured: false` steers to generating a PIN; the live
  `pairing_result` (`invalid_pin`, `pin_not_set`, `pairing_failed`) wins. The
  runtime limits failures per device and address (10, then 2 minutes;
  `syncPairFailureTracker.ts`).
- **Browsers** are never paired from the phone.
- **Background refresh.** `BGAppRefreshTask` and
  `com.ade.ios.activity.refresh` (earliest 15 minutes) refresh the snapshot and
  widget timelines; a silent push does too.
- **Widgets** (`ADEWidgets/`, rules in
  [push-notifications.md](push-notifications.md#widgets-and-freshness)):
  `ADELockScreenWidget` and the `agent-runs` Live Activity. The snapshot's
  `connection` wire string keeps `"syncing"`; do not remove it.
- **Push and Live Activity** (pipeline in
  [push-notifications.md](push-notifications.md)): signed-in phones register
  with the account relay with a persisted `ownershipEpoch` (sign-out commits an
  unowned epoch first). `ADE_APPROVAL` notification actions call `chat.approve`
  without opening the app. `LiveActivityService` owns one account-wide activity
  and ends one whose epoch does not match. Settings › Push delivery shows
  registration and relay reachability. Simulators get no real pushes.
- **Activity drawer** (`Views/Activity/`, shared rules in
  [push-notifications.md](push-notifications.md#ios-activity-drawer)): one drawer
  for the account; Sessions by the four columns and an Inbox. Live paired-host
  rows are merged over relay rows. Approve and Deny connect to the payload's
  `accountMachineKey` first and never use the focused machine instead; a tap that
  cannot open lands on the Hub with a notice. `ActivityBoardColumn` is pinned to
  `activityBoardColumn.cases.json`.

## Tab structure

### Root shell

`ContentView.rootTabs`: Work, Lanes, PRs, Files, CTO; Settings is a sheet. The
CTO tab badges from `cto.getAttention`, because the CTO chat is in no roster.
A screen hides the tab bar with `.adeRootTabBarHidden()`.

### Hub and machines

- `HubScreen` lists projects across machines (merged by origin), each opening to
  chats by lane from the roster.
- **Fleet.** The focused machine has the full connection; up to seven more keep
  light roster connections (`MachineFleet.liveMachineLimit` = 8). Opening a
  project connects every machine with a copy. A machine the user disconnected
  stays off (`ade.fleet.userDisconnectedMachineKeys.v1`).
- **One list.** Lanes and Work list every machine's rows together; a dropped
  machine's rows stay 20 s. DAEX Cloud rows always list and never wake.
- **Safety.** Chat commands go to the chat's machine and fail while it is
  offline; they never queue or fall back to the focused machine. Profiles never
  merge across device identities. Bonjour matches a saved machine by device id
  first.
- **Personal chats** (Hub card → `PersonalChatsScreen`) merge every live
  machine that advertises `personalChats.list`; every action goes to the chat's
  machine.
- **Roster over the local cache.** Local rows win by id, except turn liveness:
  `RemoteRosterChatStatus.applyingTurnState(to:)` lays the roster's
  running/waiting/idle over the local row.
- **Terminals on another machine** open over that machine's roster connection
  when it advertises `rosterTerminal`; otherwise the tap focuses the machine
  first. The CLI message bar sends `chat.typeIntoCli` to the session's computer.

### New-lane chat launches

A new chat on the auto-create-lane target uses `chat.startLaunch` when
`SyncService.canStartChatLaunch` holds; CLI, Cursor Cloud, offline and older
hosts use `lanes.create` → `chat.create` → `chat.send`. `WorkChatLaunchGate`
shows the pending screen until the agent starts. Words mirror
`shared/chatLaunch.ts` (`WorkChatLaunchPresentation.swift`). Other projects get
no pushes, so the phone polls `chat.listLaunches` for running launches (connect,
foreground, every 3 s on the Hub). See
[Chat › New-lane launches](../chat/README.md#new-lane-launches).

### The composer

- Swipe down folds it and lowers the keyboard; no fold path scrolls the
  transcript (`workComposerFoldTransition`, `workComposerFoldGesture`).
- Send lowers the keyboard. Composer text views never change first responder
  inside `updateUIView`.
- **Attachments** (`WorkComposerAttachmentStaging.swift`): images via
  `chat.saveTempAttachment` (up to ten, JPEG); video and documents via the
  chunked `chat.beginTempFileAttachment` route up to 50 MB
  (`workChatFileAttachmentMaxBytes` mirrors `MAX_CHAT_ATTACHMENT_BYTES`; change
  both). Personal chats are images-only.
- **Drafts and scheduled sends** (`WorkDraftScheduleSheet`) need the
  `chat.*Draft` actions; attaching a draft claims it first.
- **Chips** (`WorkComposerTypedTriggers.swift`, `WorkThreadEntityRules.swift`)
  port the desktop chip and thread-entity rules.
  `apps/desktop/src/shared/__fixtures__/chipCases.json` is shared by
  `shared/chips.test.ts` and
  `ADETests/WorkComposerTriggerDetectorTests.testMatchesSharedChipFixture`. Skill
  chips open `chat.getSkillInstructions`.

### Importing sessions

`WorkImportSessionScreen` uses `work.listExternalSessions`,

### Settled lifecycle and attention parity

`WorkSessionCanonicalState.swift` and `WorkSpawnNesting.swift` mirror
`shared/sessionCanonicalState.ts` and `sessionSpawnNesting.ts` (tests catch
drift).

- **The phone never writes the settle columns** (`settled_at`,
  `settle_override`, `settle_source`) or the activity-report columns; the host
  decides them and drops phone copies. Instant feedback comes from
  `PendingSessionSettleStates` (local, 20 s backstop) and
  `PendingAttentionClearStates` (8 s, inert after any host change). Both apply in
  `localSessions()`.
- Snooze is a synced overlay the phone may write
  (`Database.updateSessionSnoozeOverlay`), never a phase.
- **Add each new `terminal_sessions` column to both** `DatabaseBootstrap.sql`
  and the `ensureColumn` migrations.
- `hubChatBoardState` is the Swift copy of the brain's `rosterBoardColumn`.

### Work session list rows

The Work list ports the desktop sidebar card: **interaction owns the card
surface; state never spends it** (no provider tint; amber means "your move").
Three lines (`WorkSessionRowCard.swift`): where (lane, git state, model or time)
plus one status slot; title and PR badge; preview and provider mark. Lane names
use `LaneSummary.displayName` ("Main checkout"). The status slot may show the
host's activity (Planning, Exploring, …); **Needs you** wins. Same-lane subagents
of a chat nest under it. Non-chat sessions delete through `work.deleteSession`;
**Dismiss & settle** sends `session.settleSessions` with `dismissPendingInput`
([remote commands](remote-commands.md#registry)).

### Lane tool chips and the Work tools sheet

Read-only mirrors of the desktop Work tools, except Mac Desktop (watch, take

simulator, **macOS**, browser, App Control, each gated on its action and asked

### Settings

The connection header sits above Account, Preferences, this repository and this
device. Sections receive plain snapshots from
`SettingsConnectionPresentationModel` and never read `SyncService`.

  with its own stores and quota snapshot). `providerAccounts.list`, `getSettings`

## Data projections

- **Project switch.** Projections read `Database.currentProjectId()`. A switch
  activates the project and the phone reconnects on the same port. Cursors are
  per host DB site. Before the old connection goes, chat and terminal
  subscriptions reset so the phone never resubscribes to the old project's ids.
  `hello_ok` is the barrier; later work runs in `schedulePostHelloWork`.
- **Revisions.** Screens reload on their own projection revision
  (`lanesProjectionRevision`, `workProjectionRevision`, `prsProjectionRevision`,
  `prsRemoteRevision`, …). `LanesTabShell` and `PRsTabShell` narrow
  `SyncService` into `Equatable` inputs: **a field the body reads must be in the
  struct.**

### PR data

- One command, `prs.getMobileSnapshot`: PRs, stacks, per-PR action capabilities,
  create eligibility, and `live`. Merged-row fields (`detached`, `mergedBy`,
  `mergeMethod`, …) are optional, because old hosts lack them.
- `prs_updated` invalidates the list; the view coalesces 300 ms.

### PR detail screen

`PrDetailScreen.swift` and its helpers; the layout changes often. Contracts:

- GitHub HTML becomes safe Markdown; only GitHub-served media loads
  (`prIsGitHubMediaURL`).
- **Next step** (`PrNextStep.resolve`, port of `resolvePrNextStep`) reads merge
  state only from the PR snapshot.
- **The phone never decides CI**: every surface reads the host's `checksStatus`
  (`passing | failing | pending | none | not_run`).
- A PR with no row opens as `gh:owner/repo#number` via
  `prs.getMobileGithubDetail`.
- Derived models are built in `recomputeDerivedModels()`, never in `body`.
- Merge, close, reopen, comment and edit go through
  `SyncService.runDurablePrAction`. Sidecars reload behind a 25 s freshness
  window. Live checks poll `prs.getChecks` every 45 s while CI runs.

## Gotchas

### Data, sync and connection

- **Screens observe `SyncMenuSafePublisher`, not `SyncService`.** It holds
  publishes while a context menu is open (a connected phone publishes ~15×/s and
  SwiftUI rebuilds open menus). Use `@ObservedObject private var syncPublishes =
  SyncMenuSafePublisher.shared`, never `@EnvironmentObject var syncService`.
- **The local DB is the read source.** Fix stale reads on the runtime push side.
  Personal chats are the exception.
- **Regenerate `DatabaseBootstrap.sql`** when `kvDb.ts` changes, and add each new
  replicated column to `Database.swift`.
- **Model catalog size.** `chat.modelCatalog` sends only connected OpenCode
  providers (the full directory is ~4.85 MB); weigh any growth against the
  phone.
- **Keychain survives uninstall**; Forget machine clears Keychain and the draft.
- **Trust reset** (`MobileTrustResetPolicy`) clears connection state once and
  keeps Clerk keys, device id, DPoP identity and PIN state.
- **Direct trust outlives account access**: never make a directory-adopted
  profile depend on Relay. Directory `online` is only a 90 s lease.
- **Latency over throughput**: batch bulk work into one command.
- **New transport code must bump `lastInboundMessageAt`.**
- **The chat-summary cache merges by id**; a partial refresh must not drop the
  open chat's summary.
- **Phone file edits have no read-only gate** (`mobileReadOnly` blocks nothing).

### Chat stream

- **`seq` is a resume cursor, not an identity**; `AgentChatEventEnvelope.id`
  includes the timestamp. The engine keys on durable `sequence`.
- **One `ChatThreadEngine` per warm chat** (8 most recent plus live turns) with
  `ChatLogStore` on disk per (machine, session, scope). A "row too large"
  stand-in lives in memory only and is never a cursor.
- **Snapshot decode is element-lossy** (`@ADELossyArray`); keep new decoders
  tolerant.
- **Assistant rows key on `messageId`** (`workAssistantMessageStableId`) so live
  and canonical rows reconcile; fragments merge with `mergeWorkStreamingText`.
- **A graduated steer renders once** (`pruneResolvedQueuedSteerEnvelopes`).

### Sends and drafts

- **A live chat send is never replayed after an unclear failure.**
- `WorkActiveSendCapability` hand-mirrors `ACTIVE_TURN_DISPATCH_MODES`
  (`apps/desktop/src/shared/types/chat.ts`); active-turn sends carry
  `dispatchMode`. A non-throwing `chat.dispatchSteer` with no `dispatchedAt` is
  not a delivery.
- **Drafts are a store** (`WorkDraftPersistence.swift`): restore only into an
  empty field; a send owns the draft until the host confirms; never save an
  `isSecret` answer.
- Upload waits are bounded (`WorkComposerAttachmentUploads.resolve`).

### Pending input

- A swept gate is marked, not deleted; the host decides
  (`workPendingInputSweepState`, `resolved(hostPendingInputItemId:)`).
  `derivePendingWorkInputs` must stay `liveItems`, or the widget over-claims.
- First receipt wins (`workPendingInputResolutions`).
- Size a pending card from the chat surface
  (`workPendingInputMaxHeight(chatSurfaceHeight:)`), so Send stays reachable.

### Terminals and providers

- `parseCliProvider` accepts `claude | codex | cursor | droid | opencode |
  shell`; the phone cannot pass `command` / `startupCommand` (built from
  `apps/desktop/src/shared/cliLaunch.ts`). `workResolveCliProvider` mirrors
  `resolveCliProviderForModel`; a new provider needs both.
- An ended agent CLI continues through `work.sendToSession`.

### Activity and DAEX Cloud

- Device ownership is epoch-ordered; do not replace it with task cancellation.
- Account routes keep `accountMachineKey` everywhere.
- Drawer dismissals are pruned against live ids.
- **A cloud open must not wake** (`wake: false`); a read that wakes costs money.
- Cloud rows have no live link; a host command takes the queue or wake path.
- A cloud send keeps its message id across retries.
