## CTO surface

### 1. `getUsageSnapshot` and `listPullRequests` overflow the tool-result limit
- **Status:** still exists.
- **Severity:** medium.
- **Evidence:**
  - `apps/desktop/src/main/services/ai/tools/ctoOperatorTools.ts:3398-3406` returns `usage.getUsageSnapshot()` whole.
  - I measured the saved output from `01-oversized-tool-outputs-sizes.txt`. The `costs` array is 499,960 of the about 510,000 JSON characters. Escaping in the MCP text then doubles it to 976,000. The `windows`, `accounts` and `pacing` fields together are only about 9,000 characters.
  - Inside `costs`, the `dailyTokenBreakdownByPreset` field holds most of the data, for example 138,835 characters for `claude` and 145,867 for `codex` (type at `apps/desktop/src/shared/types/usage.ts:846`).
  - `listPullRequests` (`ctoOperatorTools.ts:1212-1226`) has no state filter and no limit. The saved output holds 147 PRs (136 merged, 5 closed, 6 open) at about 1,200 characters each.
- **Likely cause:** the CTO tools pass the full UI data shapes through. No commit since v1.2.121 changes either tool.
- **Where to fix:**
  - Give `getUsageSnapshot` a compact default: windows, accounts and pacing, with costs as totals. Add an opt-in flag for the daily breakdowns.
  - Give `listPullRequests` a `state` filter (default `open`) and a `limit`, as other CTO list tools already have.

### 2. Scheduled CTO turns fail at the usage limit with no retry, and the auto-resume ran late
- **Status:** still exists. Part of it is by design.
- **Severity:** medium.
- **Evidence:**
  - In `02-cto-scheduled-work.json`, the 07:37Z and 08:07Z jobs show `status: completed` with the outcome "You've hit your session limit". So the list shows a failed turn as done.
  - A scheduled wake is delivered as a normal turn (`apps/desktop/src/main/services/chat/agentChatService.ts:73218-73252`). The scheduler then closes the row. Nothing replays the scheduled prompt after the reset. The auto-resume sends only a generic "continue" prompt.
  - **Why the auto-resume ran 80 s late:** the CTO's own 08:31:00 check was running when the 08:31:30 auto-resume came due. The scheduler defers a busy chat in 20 s steps (`BUSY_DEFER_RETRY_MS = 20_000`, `apps/desktop/src/main/services/chat/chatScheduledWorkScheduler.ts:154`, `armBusyDeferRetry` at `:528`). It fired at 08:32:50, when that turn ended.
  - A scheduled wake does not cancel a pending auto-resume (`agentChatService.ts:59166-59169`, the `!metadata?.scheduledWake` exemption). So after the 08:31 check had done the work, a second "continue" turn still ran (`00-cto-transcript.json` entries 16-17).
  - The shared account is not a defect. The CTO chat uses the machine's default Claude account, like other chats. The owner can move it with `ade chat continue-on-account`.
- **Where to fix:**
  - When a scheduled wake starts a turn after the limit reset, cancel the session's pending auto-resume.
  - Give a scheduled row a distinct outcome (for example `failed: usage limit`) when its turn ends on a usage limit, not `completed`.

### 3. `spawnChat` cannot choose the provider account

- **Where to fix:** add `instanceId` and `credentialId` to `spawnChat` and pass them through `spawnRemoteChat`. List both flags in `ade chat create --help`.

### 17. `ade health` shows idle chats as "still running"
- **Status:** still exists. Reproduced now: `ade health --text` in the ADE project prints `[warning] 53 chats still show as running`.
- **Severity:** medium.
- **Evidence:**
  - The health check reads `terminal_sessions` rows with `status = 'running'` and flags each one whose `owner_pid` is dead (`apps/ade-cli/src/services/projects/projectHealth/projectHealthService.ts:439-451`; `processAlive` at `:300`; message at `:556-566`). It does not filter by tool type, so shells count too.
  - For a chat row, `running` means "the chat is open". The row keeps the pid of the last brain that ran it. `ade chat list` reads idle or active from the chat service instead. For example, `0ae9fe83…`, `00d286ed…` and `2075ad7b…` show `status: idle`, `runtimeAlive: false`.
