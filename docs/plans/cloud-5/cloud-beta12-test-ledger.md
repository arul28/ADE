14. **First cloud lane fails at "Make computer": "this project has no GitHub origin"** (Cloud 3, owner 2026-11-11, beta.12). Launch `2a06da66-e3f9-47d8-9536-e41898ecb210`, Small, DeepSeek, Auto-create lane, project ADE (origin `https://github.com/arul28/ADE.git` on the Mac Studio, checked). Send was allowed, then main refused. Likely cause (code read, not proven live): the composer and main read the origin two different ways. The composer (`useAdeCloudDraft.ts` via `originUrlForBinding`, `lanes/laneMachines.ts:217`) uses the tab binding's stamped origin or one it remembered from the project lists; main (`registerCloudLaneLaunchIpc.ts`) gets only the binding's stamped `gitOriginUrl` (`preload.ts` `cloudLaneLaunchSource`) or, for a local tab, reads `.git/config`. A tab opened from another computer (remote binding) with no stamped origin passes the composer check and fails in main. To confirm: which computer the window's ADE project is opened from. Fix: one origin source for both, and main asks the project's own machine when the binding has none. Severity: blocker (no cloud lane can start from such a tab). NOT built.
    - CORRECTION 2026-11-11: the owner reopened the tab from the MacBook's OWN copy ("open from a location on this Mac") and got the same refusal. So the remote-binding reading above is not the whole cause. For a local tab main reads `.git/config` itself (`readGitOriginUrlWithoutGit`, `recentProjectSummary.ts` ~358), which gives up on an `[include]`, `worktreeConfig`, more than one origin url, or a quoted value; the MacBook's config could not be read from the coordinator (MacBook refused `ade files pull`). The lane must reproduce it on the MacBook with logs first. Likely fix either way: main falls back to `git config` (`readGitOriginUrlFromConfigOrGit`) or the project's known origin.
    - Checked 2026-11-11: both computers have ADE with the GitHub origin (MacBook `project_474a7274…` at `/Users/arul/ADE`, Mac Studio `project_f141168b…` at `/Volumes/Dev/Projects/ADE`). The owner's link points at the Mac Studio's project (`accountMachineKey=654f9f8e…`, `projectId=project_f141168b…`), so the MacBook window works in the Mac Studio's copy over the connection: the remote-binding case above. Not addressed by PR #2165 (multi-machine project lifecycle, open): its diff doesn't touch `cloudLaneLaunchSource` or the IPC origin read. Fix it in our lane.
